# iCloud Universal Clipboard (UCB) 诊断 + 前提

iOS DuoPaste tap 复制后期望 Mac 端 daemon 在几秒内 capture 同条内容。这条路径**不**走 DuoPaste 自己的 mesh —— iOS 写 `UIPasteboard.general` 后,Apple iCloud UCB 把内容同步到 Mac `NSPasteboard.general`,Mac watcher 看到 changeCount 跳变才 capture。任何一段断了都会让"复制不顶"。

# 必要前提 (UCB 本身的)

UCB 是 Apple 系统服务,不是我们能控制的。两端必须同时满足:

1. **登录同一 Apple ID**(iCloud,不是 iCloud+ 订阅,免费版即可)。两台机器的 iCloud 设置里"Universal Clipboard"开关都要打开
2. **同一 Wi-Fi 网络**(或都连到同一 Apple ID 的 Personal Hotspot)。**只是 Tailscale 同网络不够**——UCB 不走 Tailscale,走 Apple 自家的 Bonjour + iCloud 通道
3. **蓝牙打开**(两端,UCB 用 BLE 做 handoff 触发信号)
4. **Handoff 总开关打开**:
   - Mac: System Settings > General > AirDrop & Handoff > "Allow Handoff between this Mac and your iCloud devices"
   - iOS: Settings > General > AirPlay & Handoff > "Handoff"
5. 两端时间没差太多(iCloud 同步对系统时间敏感)

# 4 步诊断

按顺序跑,定位断点:

## 步骤 1: 验证 UCB 物理通道

不用 DuoPaste,纯系统 app 验证 UCB 本身通不通:

```
iOS Notes 选一段文字 → Cmd+C(系统快捷键)/ Share menu 选 "Copy"
↓ (5s 内)
Mac TextEdit / Notes / 任何 app → Cmd+V
```

**期望**:粘贴到 iOS 复制的内容。
**失败**:UCB 本身没开通,跟 DuoPaste 无关。回到上面"必要前提"逐条检查,常见漏点:
- 没登录 iCloud(或登录了但 Handoff 子开关关了)
- 两端不同 Wi-Fi(企业网常有多个 SSID 看着同名实际不同 VLAN)
- iOS 蓝牙开关在 Control Center 关掉的——必须在 Settings > Bluetooth 真开

## 步骤 2: 验证 DuoPaste iOS → UCB 写入

```
iOS DuoPaste 任意条目 → tap (触发 copy)
↓ (5s 内)
Mac TextEdit Cmd+V
```

**期望**:粘贴到 iOS 那条内容。
**失败但步骤 1 通过**:DuoPaste iOS 没正确写 UIPasteboard。检查 `iOS/DuoPaste/HistoryCellView.swift` 的 `triggerCopy` 实现。多见原因:写错 type / 写空 / 没在 main thread。

## 步骤 3: 验证 Mac daemon 看到 UCB

```
iOS DuoPaste 任意条目 → tap
↓ (5s 内)
tail -20 ~/Library/Logs/duo-paste/duo-pasted.err.log
```

**期望**:看到 capture 相关日志(`capture inserted` / `capture merged`,或 `capture skipped` + 原因)。
**失败但步骤 2 通过**:UCB 把内容送到 Mac 但 Mac daemon 没 capture。可能原因:

- **Watcher 跳过了 marker type**:`PasteboardWatcher.swift` 的 `skipMarkerTypes` 含 `org.nspasteboard.TransientType` / `ConcealedType` / `AutoGeneratedType` 等。如果 iOS 端写 pasteboard 时被某 system handoff 附加了这些 type,Mac 端会跳过。验证:打开 daemon DEBUG 日志看 `unknown types` 报告
- **CaptureService 字节守门拦下**:`max_text_kb` (默认 512) / `max_blob_mb` (默认 32) 超限被跳。日志里有 `capture skipped: tooLarge`
- **Self-pid 路径回环过滤(已撤)**:历史上有过,2026-05 撤掉,正常不应再触发。如果改回去了等于回归

## 步骤 4: 反向验证 Mac NSPasteboard 收到 UCB

```
Mac Notes → 选一段文字 Cmd+C
↓ (5s 内)
iOS DuoPaste tap 不同的一条内容(模拟干扰)
↓ (5s 内)
Mac TextEdit Cmd+V
```

**期望**:粘贴到 iOS 刚 tap 的那条(不是 Mac Notes Cmd+C 的那段)。这证明:
- Mac NSPasteboard.general 收到 iOS UCB 写入
- 后写覆盖先写,changeCount 跳了

**失败**:UCB 没把 iOS 写入推到 Mac NSPasteboard.general,本地 Cmd+C 的内容没被覆盖。这是 UCB 本身的问题(同步延迟 / 链路断),不在 DuoPaste 代码层。

# 已知不要踩的坑

- **Mac UCB 接收有 ~1-3s 延迟**——iOS 写完到 Mac 见到 changeCount 跳变常见 1-2s。daemon 跑 200ms 轮询,**最迟** 3s 内应 capture。超过 5s 没看到日志基本是 UCB 没通
- **Mac 端 watcher 跑在 LaunchAgent daemon 里**——你前台没运行 DuoPaste GUI 不影响 capture。如果 daemon 挂了 `launchctl print gui/$UID/io.duopaste.agent` 会显示非 `running`
- **不要**在两端关闭 Wi-Fi 让"只走蓝牙"——UCB 强制要求 Wi-Fi(蓝牙只做 handoff 触发)
- **iOS Control Center 关蓝牙是假关**——只断当前 session 的 BT 连接,UCB 路径用的 BT advertise 还在。**Settings > Bluetooth toggle 关掉**才是真关

# 跟 #2 (POST /bump) 的关系

UCB 路径之外,DuoPaste 还有另一条让 Mac 看到 iOS 复制的路径:**iOS 直接 HTTP POST 给 Mac daemon 让它 bump 行**(plan #2,已落地后)。两条路径并存:

- UCB 让 Mac 看到**新内容**(iOS Notes 复制 "hello" → Mac DuoPaste capture 一条 text="hello")
- POST /bump 让 Mac 看到**已有内容被 tap 顶**(iOS tap 历史里 "world" 那条 → Mac DB bump 那条 captured_at_ns)

UCB 故障时 #2 仍能让"顶"跨设备一致;反过来 UCB 通而 #2 没做时,iOS 端 tap 顶只是本机视觉欺骗,Mac 看不到。
